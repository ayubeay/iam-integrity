## 1. Observation

Software collaboration is changing from Human <-> Human to:

    Human <-> Human
    Human <-> Agent
    Agent <-> Agent

Products are beginning to place coding agents, assistants, and autonomous
workers inside shared communication environments. The emerging problem is no
longer merely enabling agents to talk. The harder problem is making shared
execution: attributable, governable, observable, verifiable, replayable,
economically fair, and trustworthy.

A chat transcript alone cannot establish who produced an artifact, which model
or agent acted, which policies applied, whether the work was verified, or how
contributors should be rewarded.

HELIX is reserved as the environment that connects identity, discovery,
collaboration, execution, verification, reputation, and economic outcomes.

## 2. Core thesis

HELIX should not be reduced to a cofounder marketplace, freelance board, chat
application, or agent directory. HELIX is reserved as:

**A truthful execution environment where humans, companies, and AI agents
discover one another, work together, produce verifiable outcomes, and build
portable execution reputations.**

Its marketplace attracts participants. Its workspace retains them. Its
execution rooms organize work. Its verification systems create trust. Its
receipts create evidence. Its economic rails compensate contributors.

## 4. Participant identities

HELIX should support multiple first-class identity modes.

**Solo Builder.** A participant who wishes to remain independent. Capabilities
may include: verified identity, verified portfolio, private workspaces,
personal agents, repositories, execution receipts, contracts, payments,
reputation, selective collaboration, customer and integration discovery.
Solo builders must not be treated as incomplete teams.

**Collaborator.** Open to: projects, cofounding, contracts, employment,
equity, revenue sharing, mentorship, internships.

**Contributor.** Examples: developer, designer, marketer, researcher, lawyer,
educator, analyst, music producer, operations specialist.

**Company or Agency.** Organizations may create and manage: employees,
contractors, clients, AI agents, projects, permissions, billing, internal
workspaces, audit records.

**Mentor or Educator.** Verified specialists may guide learners and teams
while routine instruction is handled through adaptive AI support.

**AI Agent.** Agents may possess: persistent identity, creator attribution,
declared capabilities, model and version information, permissions, endpoints,
execution receipts, performance history, trust status, cost history.

## 5. Builder stance

Profiles should clearly communicate how a participant wishes to engage.
Possible stance badges: Available for projects; Looking for cofounder; Open to
contracts; Open to employment; Open to investment; Building in public;
Heads-down building; Mentor only; Solo and unavailable; Open to API
partnerships. This prevents the platform from assuming every user wants the
same outcome.

## 6. Helix Marketplace

The marketplace answers: **who, what team, company, mentor, opportunity, or
agent should I work with?** It may support discovery of: solo builders,
collaborators, companies, agencies, mentors, interns, investors, projects,
agents, specialized services, hackathons, contribution opportunities.

The marketplace is an entry point, not the whole product. Once participants
agree to work together, they move into Helix Workspace.

## 7. Helix Workspace

Helix Workspace answers: **how do we work together?** Potential capabilities:
messaging, voice, video calls, documents, shared knowledge, whiteboards,
tasks, repositories, APIs, agent orchestration, meetings, reviews, approvals,
deployments, payments, contracts, execution timelines, receipts.

HELIX does not need to replace Slack, Zoom, GitHub, Notion, and every existing
tool immediately. Early versions may integrate those systems while HELIX
provides the identity, governance, execution, verification, and receipt layer
joining them together.

## 8. Execution Rooms

Execution Rooms are reserved as the primary unit of governed collaboration
inside Helix Workspace. An Execution Room is not merely a chat channel. It may
contain: human participants, AI participants, conversation, objectives, task
queues, permissions, artifacts, code, documents, calls, decisions, approvals,
challenges, execution receipts, deployments, payment milestones, replay
timelines.

Lifecycle:

    Objective declared
        -> Participants assigned
        -> Permissions established
        -> Tasks delegated
        -> Humans and agents execute
        -> Artifacts produced
        -> Work challenged or reviewed
        -> Decision approved
        -> Deployment or delivery
        -> Receipt stored
        -> Reputation and compensation updated

Chat remains one panel within the room rather than the central architectural
object.

## 9. Agent Collaboration Layer

Reserve future support for multiple autonomous agents collaborating
synchronously or asynchronously in shared workspaces. Research areas:
identity-bound agents, task delegation, agent-to-agent messaging, shared
memory, capability discovery, execution provenance, challenge workflows,
conflict resolution, verification, replay, model disclosure, policy
enforcement, failure containment.

Each consequential agent action should be capable of carrying fields such as:

    agent_id, creator_id, model_id, model_hash, prompt_hash,
    policy_version, workspace_id, execution_id, timestamp,
    input references, artifact references, verification status,
    challenge history, cost, outcome

The purpose is not to make agents converse socially. The purpose is to make
collective machine execution accountable.

## 10. Helix Verified

HELIX should verify execution rather than merely applying a cosmetic identity
badge. Possible verification dimensions: identity, portfolio ownership,
project availability, repository activity, commits, reviews, deployments,
documentation, execution consistency, contribution quality, customer outcomes,
collaborator feedback, agent disclosure, receipt integrity.

A profile could eventually display:

    Builder: Example User
    Mode: Solo Builder
    HELIX Score: 92
    Verified deployments: 18
    Verified contributions: 447
    Execution receipts: 1,204
    Review acceptance: 94%
    Active products: 5
    Current stance: Open to API partnerships

Self-description may remain present, but evidence should carry greater weight.

## 11. Contribution economy

Reserve support for contribution-aware compensation. Participants may be
compensated through: salary, contract fees, milestone payments, revenue
sharing, equity, bounties, royalties, mixed agreements.

Contribution receipts may reference: commits, designs, documents, code
reviews, campaigns, conversions, research, contracts, meetings, deployments,
approvals, mentorship, client outcomes.

Receipts are not intended to automatically decide ownership or compensation
without agreed rules. They provide auditable evidence so decisions are less
dependent on memory, politics, or unverifiable claims.

## 12. Internship and apprenticeship layer

HELIX should support people with little formal experience who need a pathway
to prove capability:

    Join a supervised project
        -> Receive scoped permissions
        -> Complete real tasks
        -> Receive mentor review
        -> Generate verified receipts
        -> Build portable reputation
        -> Qualify for larger responsibilities

The platform becomes a mechanism for converting real contribution into career
evidence. A degree or resume may remain useful, but it is no longer the only
trust signal.

## 13. Ethical execution doctrine

HELIX should encode ethical principles into observable system behavior rather
than relying only on slogans. Reserved principles:

1. Truth before opinion.
2. Evidence before authority.
3. Execution before reputation.
4. Contribution before reward.
5. Stewardship before ownership.
6. Learning before scaling.
7. Receipts before claims.
8. Human agency before hidden automation.
9. Permission before execution.
10. Challengeability before irreversible action.

Team leaders should be treated as stewards responsible for: team health, fair
contribution, permissions, security, AI governance, delivery, dispute
handling.

## 14. Adaptive guidance inside HELIX

Reserve an adaptive learning capability that helps users understand systems
while preserving autonomy. Core concepts: progressive scaffolding, offered
choice rather than forced action, just-in-time explanations, knowledge
mapping, gradual reduction of assistance, restoration of assistance when
requested.

    New user
        -> High visibility and frequent confirmation
        -> Demonstrated competence
        -> Reduced prompts and greater autonomy
        -> Anomaly or uncertainty
        -> Scaffolding restored

May support: developers, interns, traders, operators, companies, Earthwise
workers, SoundKeep learners, EventPulse or SportGPT users. A shared
human-learning capability, not necessarily a standalone education product.

## 15. Trading as a future vertical

Trading must not define HELIX. It may serve as one future vertical for
governed execution. HELIX should not initially become a broker or hold
customer funds.

    HELIX Workspace
        -> Connected regulated broker
        -> AI teacher / copilot / programmed agent
        -> Risk policy
        -> VERITY and vLOID checks
        -> Human approval where required
        -> Broker executes
        -> Receipt stored

Modes: **Teacher** (explains pips, leverage, margin, risk, outcomes; cannot
execute trades). **Copilot** (analyzes proposed trades, recommends sizing,
warns about spread/margin/volatility/policy breaches; user remains
decision-maker). **Programmed Agent** (follows explicit strategy and risk
rules, operates only within permissions, produces receipts, remains subject
to policy and jurisdictional requirements).

Trading agents may later appear in RACER as FinAgents, but HELIX itself
remains a general execution environment.

## 16. RACER relationship

RACER retains its existing role as the agent economy platform. It answers:
**which agent should I discover, compare, acquire, or deploy?** It may
display: capability, creator, supported tasks, pricing, benchmarks,
historical outcomes, trust information, risk tiers, receipt summaries.

After selecting an agent, the user deploys it into Helix Workspace. RACER is
not replaced by the human builder marketplace. The distinction:

- Helix Marketplace: humans, teams, companies, projects, opportunities.
- RACER: AI agents and agent services.
- Helix Workspace: execution environment for both.

## 17. HELIXCAN relationship

HELIXCAN is reserved as the explorer for AI agents and execution records. It
is not the agent marketplace and not primarily an analysis engine. HELIXCAN
answers: **show me what happened.**

It may expose: agent IDs, creators, versions, workspace references,
executions, tasks, policies, outcomes, receipts, costs, artifacts,
permissions, linked agents, challenge records, trust history.

    RACER        — discover an agent
    Workspace    — run the agent
    vLOID/VERITY — govern the execution
    HELIXCAN     — inspect the public or permissioned record

## 18. HelixAtlas relationship

HelixAtlas is the visual execution-map layer. It may visualize: human and
agent participants, execution routes, gates, dependencies, receipts,
decisions, challenges, artifacts, failures, retries, approvals, system
topology.

HelixAtlas does not replace Workspace or HELIXCAN. Workspace is where work
occurs; HELIXCAN exposes records; HelixAtlas renders execution journeys and
system relationships.

## 19. HelixMeter relationship

HelixMeter measures the true economics and dependency profile of execution,
extending beyond token counting. Potential measurements: model costs, tool
costs, infrastructure, retries, latency, human review, failed executions,
provider concentration, switching difficulty, outcome quality, cost per
verified result.

Guiding idea: **rent intelligence, own execution.** HelixMeter may answer:
what did the complete outcome cost; which provider created the dependency;
what percentage of workflows would fail if a provider disappeared; which
execution path produces the best verified outcome per dollar; where can work
be safely rerouted.

## 20. Helixwap relationship

Helixwap remains the transformation and execution rail. Future scope may
include routing: model calls, agent services, broker operations, blockchain
actions, payments, cloud jobs, SaaS actions, API requests.

    Intent
      -> Admissibility
      -> Capability selection
      -> Execution route
      -> Action
      -> Receipt
      -> Settlement

Helixwap should not be reduced to only a crypto swap interface.

## 21. vLOID integration

vLOID remains the execution-admissibility infrastructure beneath HELIX.
Relevant responsibilities: identity continuity through IAM, doctrine through
LITMUS, orchestration through OROS, trust through VERITY, drift detection,
permission boundaries, receipts, governance decisions.

HELIX provides the environment and user-facing platform. vLOID constrains
what participants and agents may do within it.

## 23. Adoption sequence

HELIX should not launch initially as an enormous empty network.

**Phase 0 — Internal proof.** Use existing ecosystem projects to generate
real examples of deployments, contributions, agent executions, receipts, cost
records, verification, collaboration. Candidates: API Connect, SoundKeep, POI
Engine, KONIGO Connect, Momentum Sniper records where appropriate, future
EventPulse or SportGPT work.

**Phase 1 — Verified profiles.** Launch execution identity for solo builders
and small teams. Initial value: proof of work, portfolio verification,
deployment receipts, stance badges.

**Phase 2 — Marketplace.** Enable discovery of builders, teams, projects,
mentors, companies.

**Phase 3 — Workspace and Execution Rooms.** Move matched participants into
governed collaboration environments.

**Phase 4 — RACER agents.** Allow verified agents to be discovered and
deployed inside workspaces.

**Phase 5 — Economic and enterprise layers.** Payments, revenue splits,
company controls, audit, advanced governance, migration and execution
infrastructure.

## 24. Non-goals

This reserve does not authorize: building another generic Discord clone;
copying LinkedIn or Upwork feature for feature; replacing every collaboration
tool in the first version; treating chat as the primary innovation; forcing
all builders into teams; making RACER redundant; redefining HELIXCAN as an
analytics engine; turning HELIX into a broker; launching autonomous financial
execution without legal, policy, and risk controls; allocating compensation
automatically from raw activity counts; beginning full implementation before
the initial wedge is defined.

## 25. Initial wedge candidates

Future product selection should identify a narrow pain rather than beginning
with the entire platform. Possible wedges: verified solo-builder execution
profiles; contribution receipts for small teams; governed AI execution rooms;
agent provenance for software teams; internships based on real verified work;
human-plus-agent project workspaces; company dependency and execution cost
visibility.

The wedge should satisfy: clear user; clear pain; observable outcome; small
build surface; credible distribution path; revenue possibility; architectural
compatibility with HELIX.

## 26. Future research extensions

**Legacy execution migration.** Map old systems, workflows, dependencies,
permissions, failures, and business importance before AI-enabled
modernization:

    Discover legacy system
        -> Build execution graph
        -> Score what should be retained
        -> Propose migration
        -> Human approval
        -> HELIX executes
        -> VERITY validates
        -> HELIXCAN records

**Multi-output execution assets.** A single execution may produce: completed
work, receipts, trust updates, billing data, audit history, reusable
knowledge, future automation signals.

**Physical HELIX presence.** Only after software validation: HELIX Chapters,
HELIX Labs, HELIX Houses, HELIX Studios — physical spaces providing verified
builders with education, community, and company formation support.

## 29. Guiding philosophy

HELIX is reserved around a simple proposition: **work should create
evidence.** A person, team, company, or agent should be able to grow through
repeated cycles of:

    Discover
       -> Connect
       -> Execute
       -> Verify
       -> Receive outcome
       -> Build reputation
       -> Take greater responsibility
       -> Help others execute

Each cycle should leave participants with greater capability, evidence,
trust, and opportunity. That is the transformation represented by HELIX.
