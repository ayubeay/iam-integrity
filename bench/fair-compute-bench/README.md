# fair-compute-bench — Milestone A (native Rust)

Scope and doctrine: [`docs/browser-fair-compute-reserve.md`](../../docs/browser-fair-compute-reserve.md).

This is the first build in the browser-fair-compute reserve. It is deliberately
small: **one deterministic workload, native only.** No WebAssembly, no browser,
no token, no network, no telemetry.

## Why native first

The reserve's build queue puts WebAssembly second on purpose. The browser
comparison is the *experiment*; it is only valid if the wasm build runs the
**same implementation**, not a port of it. Establishing that the workload is
correct and deterministic in one environment first means any difference observed
in Milestone B is attributable to the runtime rather than to a transcription
difference between two implementations.

`src/workload.rs` is the file Milestone B will compile to `wasm32` unchanged.
Everything else in this crate is harness.

## The workload

A serial dependent-memory-access chain over a power-of-two scratchpad:

```
idx  = acc & mask          # address depends on the previous read
v    = pad[idx]
acc  = mix(acc ^ v) + step
pad[idx] = v ^ acc         # read-modify-write, not read-only
```

The address of step *N+1* cannot be computed until the value read at step *N*
has been mixed. The chain is therefore bound by **dependent memory latency**,
not by bandwidth and not by parallel throughput. The write-back is not
decoration: a read-only chain can be served from a replicated read-only cache
and prefetched speculatively, which would destroy the property being tested.

Constraints that make cross-runtime determinism possible:

- integer-only, `u64` with explicit wrapping — no floating point anywhere
- index arithmetic in `u64`, narrowed to `usize` only at the subscript
  (`usize` is 32-bit on `wasm32` and 64-bit natively)
- power-of-two masking, never modulo — a divider in the dependent chain would
  measure the divider
- no threads, no allocation in the hot loop, no syscalls, no I/O

**None of this makes the workload fair.** It makes it *measurable*. Whether the
fairness thesis survives Phase 2 and Phase 3 is an open empirical question, and
a negative result is an acceptable outcome.

## Correctness

Determinism is verified against `reference/reference_workload.py`, an
independent transcription of the algorithm that shares no code with the Rust.
The known-answer vectors baked into `tests/determinism.rs` were generated by the
Python reference, so the test asserts agreement between two implementations
rather than merely snapshotting whatever the Rust produced.

If you change the workload semantics, these tests **should** fail. Re-derive the
vectors with `python3 reference/reference_workload.py`; do not paste in values
from the Rust.

`reference/access_pattern_check.py` separately checks the two ways this workload
could degenerate while still producing stable, plausible-looking timings: the
chain falling into a short cycle (so everything stays in L1 forever), and
consecutive addresses turning out to be spatially close (so the prefetcher hides
the latency the workload exists to expose). Current result on the specified
parameters:

| scratchpad | steps | coverage | address cycle | consecutive accesses within 8 words |
|---|---|---|---|---|
| 1024 words | 20,000 | 100.00% | none | — |
| 4096 words | 40,000 | 100.00% | none | — |
| 65536 words | 200,000 | 95.35% | none | 0.028% |

Both gates run as part of:

```
./verify.sh
```

## Running

Always `--release`. A debug build measures the absence of the optimiser; the
harness prints a warning if you forget.

```
cargo run --release -- --help

# default: 32 MiB scratchpad, 20M dependent accesses, 7 timed runs
cargo run --release -- --json results/native-baseline.json

# sweep the scratchpad past the cache hierarchy — this is the interesting curve
for mib in 1 2 4 8 16 32 64 128 256; do
  cargo run --release -- --scratchpad-mib $mib --steps 5000000 \
    --json results/native-${mib}mib.json --label "cache sweep"
done
```

The scratchpad is re-initialised **before every timed run** and initialisation
is **excluded from the timed region** — it is a streaming write and would
contaminate a latency measurement with a bandwidth measurement. Because runs are
independent, all digests must be identical; if they are not, `determinism_ok` is
`false` and the harness exits non-zero.

## Reading the output

`ns_per_step` is the headline number: average latency of one dependent access.
Expect it to track the memory hierarchy — a few ns while the scratchpad fits in
cache, rising toward DRAM latency as it does not.

`relative_spread` is the honesty check. Above ~5% the machine was not quiet
(thermal, other load, frequency scaling) and the numbers should not be quoted in
a report. Close other applications, disable turbo variability if you can, and
re-run.

## JSON schema

`schema: "fair-compute-bench/1"`. **The Milestone B browser harness must emit
this identical schema**, so that native and wasm results are directly
comparable without a translation step. `harness.runtime` distinguishes them
(`"native"` vs `"browser"`), and `workload.implementation_hash` must match
across both — if it does not, the two are not running the same code and the
comparison is invalid.

## Milestone B — the browser harness

`web/index.html` runs the **same** `workload.rs` compiled to `wasm32`, via a raw
C-ABI export surface (`src/lib.rs`, `#[cfg(target_arch = "wasm32")]`). No
wasm-bindgen, no wasm-pack, no npm — the crate stays zero-dependency and no
framework glue enters the timed region.

```
./build-wasm.sh                 # adds the wasm32 target, builds, copies the .wasm into web/
cd web && python3 -m http.server 8000
# open http://localhost:8000/  (file:// cannot fetch the wasm)
```

The page enforces the product doctrine from the reserve at the code level: it
does **nothing until you press Start**, runs only in the focused tab, has a Stop
control, makes no network calls, and does no background execution. There is no
auto-run path.

On load it runs the five known-answer vectors and shows pass/fail against the
native reference, and it prints the wasm `implementation_hash` for you to
eyeball against the native binary's `implementation` line. The determinism claim
is exactly this: **browser and native must produce byte-identical digests for
identical parameters.** The algorithm has already been cross-verified across
three independent implementations — Rust, `reference/reference_workload.py`, and
a JavaScript/BigInt re-derivation — so a wasm digest that disagrees means the
build, not the algorithm, is wrong.

Results download as JSON in the **same `fair-compute-bench/1` schema** the native
runner emits (`harness.runtime` is `"browser"` vs `"native"`), so Milestone C is
just laying the two curves on one axis. Browser timers are deliberately coarsened
by the engine, so the page reports `min` prominently and warns when relative
spread exceeds 5%.

Milestone C does not begin until `./build-wasm.sh` succeeds and the page's
known-answer check passes on the target machine.

## Milestone C — the comparison

`compare.py` (zero-dependency, stdlib only) turns a directory of result JSONs
into the first research artifact: the browser-to-native efficiency ratio per
scratchpad size. It is the number that speaks to the reserve's core question.

```
# 1. native sweep
for mib in 1 8 32 128 256; do
  cargo run --release -- --scratchpad-mib $mib --steps 5000000 \
    --json results/native-${mib}mib.json --label "M-series baseline"
done

# 2. browser sweep — open web/index.html, Start at each size, Download JSON
#    into results/ as browser-<n>mib.json

# 3. the report
python3 compare.py            # scans results/, writes results/report/{md,csv,json}
```

Three guarantees, in priority order:

1. It **refuses to compare** runs whose `implementation_hash` differs, with a
   hard non-zero exit. If native and browser did not run the same source, no
   ratio between them is meaningful, so none is produced.
2. It reports the ratio on both `min` (least-contended, the defensible
   estimator) and `median`, and flags any size whose relative spread exceeded
   5% as not-citable.
3. It carries the reproducibility metadata — OS, CPU, logical cores, Rust
   toolchain and target (native), user agent, hardware concurrency and device
   memory (browser) — so a later run on different hardware can be compared
   without wondering whether the environment explains the difference. Power
   mode, thermal state, and browser version still need recording by hand; the
   report says so.

Native results now embed the toolchain and target via `build.rs` (no runtime
cost). Re-run the native sweep after this change so those fields are populated —
older JSONs simply omit them and the generator skips them.

What a ratio near 1.0 would mean: browser execution is competitive with native
on this workload. What it would not mean: hardware fairness. That needs Phase 2
(diverse devices) and Phase 3 (adversarial parallel replication), both still
open. Correctness parity is proven; performance parity is what Milestone C
measures; fairness is a later and harder claim.

## Not in scope

No token. No network calls. No background execution. No use of anyone's
